# PipeLLM: Fast and Confidential Large Language Model Services with Speculative Pipelined Encryption
# Summary
The core idea of PipeLLM is inspired by CPU instruction pipelining: while the GPU is actively computing, the CPU pre-encrypts the data the GPU will need next. Hence encrypted data is ready to transfer immediately upon request, effectively hiding encryption latency behind GPU computation. This pipeline is feasible because LLM memory swapping follows highly predictable patterns such as repetitive layer-by-layer offloading, FIFO, and LIFO, allowing PipeLLM to forecast both which data and at what sequence position it will be requested. Three problems must be addressed to make this work: if the predicted order within a batch is wrong, PipeLLM reorders the pre-encrypted chunks since intra-batch ordering is irrelevant to the application. If the real IV is behind the predicted IV, NOP transfers are inserted to advance the real IV counter until it matches the predicted value. Last if data is modified after pre-encryption, a read-only page protection triggers a page fault that invalidates the stale ciphertext and schedules re-encryption. The resulting overhead is reduced to under 19.6%, where most of the remaining gap is a hardware-level constraint — enabling NVIDIA Confidential Computing drops maximum bandwidth of CPU-to-GPU memory copy from 64 GB/s to 40 GB/s. Moreover, a minor security caveat is that NOP transfers and the frequency of prediction failures introduce a side channel through which attackers can infer swapping activity and the application's memory access.
# Questions
1. As agentic LLM workloads become more common, the CPU is increasingly occupied by orchestration, tool execution, and context management alongside its existing responsibilities. Does the additional CPU pressure from these tasks interfere with PipeLLM's pre-encryption threads, and could the CPU become a bottleneck in such settings?
2. Section 8.2 identifies ciphertext reuse as a potential optimization but rules it out because of replay attack risks. What specific hardware or protocol changes would be required to enable it securely?
3. How does PipeLLM handle multiple concurrent user requests within vLLM that have different KV cache eviction priorities?
