# Scale and Performance in the Denali Isolation Kernel
## Summary
Denali is an isolation kerenl that securely multiplexes a large number of untrusted Internet services on shared hardware by exposing a modified virtual machine abstraction based on x86. The Denali kernel does not emulate the instructions of VM. Instead, it modified the virtual architecture so that most instructions can directly run on the physical processor. The key design principles are exposing low-level resource, private virtual namespace, scalabilty according to Zipf principle and modifying virtualized architecture. The first two principles gives more strong isolation since lower level resouse has less attack surface and private virtual namespaces eliminate complex access control. The third principle makes scalabilty of VM more easiler because the needed resource won't be linear to the number of VM. The last principle let VM more simplified and scalible.  Key mechanisms include a batched asynchronous interrupt model that reduces context switch frequency by up to 30%, and an `idle-with-timeout` instruction that prevents idle VMs from wasting CPU cycles. Denali isolation kernel can scale up to 10000 VMs on commodity machine while maintaining low virtualization overhead.
## Questions
1. Since UDP has no retransmission, will batched, asynchronous interrupts cause additional packet loss under high VM contention?
2. Supervisor VM can create and distory the VM. How do we make sure supervisor VM is trustworthy?
3. Denali's memory management assumes a Zipf workload. How does the system perform when requests are distributed uniformly across all VMs?
# TwinVisor: Hardware-isolated Confidential Virtual Machines for ARM
## Summary
This paper proposes TwinVisor which is the first system that enables hardware-isolated confidential VM on ARM platforms by utilizing ARM TrustZone and the S-EL2 extension. The key design principle is decoupling resource management from security protection through two hypervisors: the N-visor, which resides in the normal world,  handles all hardware resource management, while the S-visor, residing in the secure world, focuses on protecting confidential VMs from unauthorized access by the untrusted N-visor. Three key mechanisms support this architecture. The first mechanism, Horizontal Trap, batches security checks at world-switch boundaries to validate N-visor operations without frequent interception. The second mechanism, Split CMA, enables dynamic adjustment of secure memory regions to conqure TZASC's hardware limitation of only eight static memory regions. The last mechanism, Fast Switch, eliminates redundant register operations during world transitions with reducing switch latency by 37.4%. Evaluation on real-world workloads demonstrates that TwinVisor has less than 5% performance overhead compared to a standard KVM.
## Questions
1. The paper evaluates compaction overhead using average throughput, but compacting 8MB memory chunks may introduce unpredictable pause times. How does Split CMA impact tail latency in latency-sensitive applications like financial transaction systems?
2. The paper assumes S-VMs handle their own I/O encryption. Why does the S-visor not provide transparent automatic encryption for I/O data? What if the ternant forgets to enable the encryption.
3. The security evaluation only validates the system against a selected set of known KVM CVEs. Has any formal verification or systematic security analysis been conducted to ensure no new attack surfaces are introduced?
