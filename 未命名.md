### Coordinated Prefetch I/O Scheduling for Concurrent Firecracker MicroVM Snapshot Restoration

_Virtual Machine Course Final Project Proposal – 3-Person Group, 2026_
# Background
Serverless computing platforms rely on fast function instantiation to meet latency SLAs. The industry-standard approach, exemplified by AWS Lambda, uses Firecracker microVMs—a lightweight KVM-based VMM written in Rust—to isolate function instances with minimal overhead. To avoid the cost of booting a VM from scratch on every invocation, production systems snapshot a fully initialized VM and restore it on demand. Firecracker implements this via lazy loading, pulling guest pages from disk as page faults occur, which keeps restore initiation fast but defers the I/O cost into the critical execution path.
# Problem Statement
Recent snapshotting systems like REAP prefetch an estimated working set of memory pages to accelerate restores, assuming that memory access remains stable across invocations. However, FaaSnap demonstrated that this assumption breaks down when function inputs vary, leading to significant performance degradation. To resolve this, FaaSnap introduces techniques like concurrent paging, per-region memory mapping, and loading sets to efficiently handle working set variance.

FaaSnap also explicitly evaluates bursty workloads, demonstrating resilience when multiple VMs concurrently restore from the same or different snapshots (multi-tenant environments). However, while FaaSnap establishes that concurrent paging is effective, its prefetching mechanism remains fundamentally _uncoordinated_. When $N$ FaaSnap loaders simultaneously fetch working sets during an invocation burst, they compete freely for underlying NVMe disk bandwidth. As density and burst concurrency scale up, this uncoordinated I/O contention may lead to queuing delays, cache thrashing, and suboptimal tail latencies (e.g., P95 restore times). It remains an open question whether explicitly scheduling concurrent working-set reads across restoring VMs can meaningfully improve tail latency compared to the competitive baseline.
# Proposed Solution
We propose building a coordinated I/O prefetch scheduler for concurrent Firecracker microVM snapshot restores. Instead of modifying the kernel, we will manage this at the VMM/Orchestrator level.
- **Implement an I/O Coordinator Daemon**: Build a lightweight userspace daemon that gates each VM's bulk working-set read, coordinating concurrent prefetch I/O across restoring VMs via a Unix-socket protocol.
- **Implement and Compare Scheduling Policies**: Develop an unscheduled baseline (VMs compete freely, simulating FaaSnap's concurrent paging), FIFO queuing, and Round-Robin I/O interleaving in configurable chunk sizes.
- **Evaluation**: Evaluate the scheduler against the unscheduled baseline using burst workloads involving different functions. We will report latency distributions (specifically tail latency), scheduler CPU overhead, and I/O utilization to determine if coarse-grained userspace scheduling improves upon uncoordinated prefetching.
# Expected Contribution
We expect to show that under high-concurrency burst loads, explicitly scheduling prefetch I/O (e.g., via Round-Robin interleaving) reduces P95 restore latency compared to the uncoordinated prefetching model established by FaaSnap. A negative result finding that uncoordinated NVMe I/O effortlessly scales without scheduling bottlenecks is equally valid and would serve to further validate FaaSnap's design choices under extreme concurrency. Either outcome contributes a valuable empirical characterization of I/O contention during multi-tenant snapshot restoration.
